# DocGen: MVP и развитие

## Зачем этот файл

Здесь собрана единая граница продукта: что входит в MVP, что оставляем на развитие, как живут шаблоны, где хранятся файлы и как закладывается расширение под другие подразделения.

## Коротко о продукте

DocGen - рабочий инструмент для подготовки документов из разрозненных источников.

Основная идея:

- загрузить Word/Pdf и при необходимости ссылки Confluence;
- выбрать шаблон и формат вывода;
- собрать черновик или проверить документ по шаблону;
- править результат через чат;
- скачать готовый файл в `DOCX`, `HTML` или `PDF` в корпоративном стиле.

## Термины

### Шаблон

`Шаблон` - это смысловая структура документа.

Он отвечает на вопрос:

- что писать;
- в каком порядке;
- какие разделы обязательны;
- как проверить полноту.

Примеры шаблонов:

- `Use Case`;
- `FAQ`;
- `Инструкция`;
- `Release Notes`;
- `Техническое задание`.

### Формат вывода

`Формат вывода` - это технический формат результата.

Он отвечает на вопрос:

- куда отдать результат;
- в каком виде его сохранить;
- какой встроенный рендер и стиль применить.

Примеры форматов:

- `HTML`;
- `DOCX`;
- `PDF`.

### Тема оформления

`Тема оформления` - это визуальный слой, который можно добавить позже.

Она отвечает на вопрос:

- как именно выглядит результат внутри выбранного формата;
- какой корпоративный стиль применить;
- как переключать визуальные пресеты без смены структуры документа.

Для MVP тема оформления в интерфейсе не показывается, но в архитектуре лучше оставить точку расширения.

## MVP

### Что входит в MVP

- выбор шаблона из предзагруженных;
- загрузка Word-документов;
- добавление ссылок;
- чат для правок и уточнений;
- проверка по выбранному шаблону;
- генерация результата;
- выбор формата вывода: `DOCX`, `HTML`, `PDF`;
- кнопки `Открыть` и `Скачать` после сборки.

### Что не входит в MVP

- загрузка pdf-документов;
- добавление новых шаблонов пользователем;
- сохранение проекта;
- повторное открытие прошлой сессии;
- библиотека пользовательских шаблонов;
- командные пространства;
- сложный редактор с отдельной зоной редактирования;
- отдельная история запусков на экране.

### Что важно про шаблоны в MVP

- в MVP шаблоны только предзагруженные;
- шаблон - это отдельная сущность, даже если кнопки загрузки еще нет;
- шаблон можно использовать и для генерации, и для проверки по шаблону;
- загрузка новых шаблонов - это развитие, а не MVP.

### Логика MVP-экрана

- слева - источники;
- в центре - чат как главная зона правок;
- справа - предпросмотр результата;
- сверху - только нужные управляющие поля;
- после `Собрать` появляется блок результата:
  - `Готово`;
  - `Открыть`;
  - `Скачать`.

### Два основных сценария MVP

#### Сценарий 1: Word -> HTML

Подходит для быстрого преобразования входного документа в красивый HTML без шаблонной подготовки.

Поток:

1. Пользователь заходит.
2. Загружает Word.
3. Выбирает `Формат вывода = HTML`.
4. Нажимает `Собрать`.
5. Получает HTML-preview и кнопку `Скачать`.

Что здесь важно:

- шаблон смысла не нужен;
- `HTML` уже подразумевает встроенное корпоративное оформление;
- результат сразу идет в готовую HTML-страницу;
- это самый короткий и дешевый поток.

#### Сценарий 2: Word + ссылки -> черновик -> правки -> документ

Подходит для более содержательных документов, где нужен шаблон и ручная доработка через чат.

Поток:

1. Пользователь заходит.
2. Загружает документы Word.
3. Добавляет ссылки на Confluence (TS?).
4. Выбирает шаблон.
5. Выбирает `DOCX`, `HTML` или `PDF`.
6. Нажимает `Собрать`.
7. Получает черновик.
8. Просит правки через чат.
9. Нажимает `Проверить по шаблону`, если нужно ревью.
10. Скачивает результат.

Что здесь важно:

- `Шаблон` нужен как смысловая структура;
- `Формат вывода` остается отдельным выбором;
- правки идут через чат, без отдельной зоны редактирования;
- проверка по шаблону и генерация - разные действия в одном workspace.

#### Сценарий 3: Готовый Use Case -> проверка по шаблону

Подходит для отдельного режима ревью уже готового документа.

Поток:

1. Пользователь заходит.
2. Загружает готовый `Use Case` или другой документ.
3. Выбирает шаблон `Use Case`.
4. Нажимает `Проверить по шаблону`.
5. Система сравнивает документ со структурой шаблона.
6. Пользователь получает:
   - слабые места;
   - недостающие разделы;
   - слишком общие формулировки;
   - что стоит дополнить;
   - что не соответствует шаблону.

Что здесь важно:

- это не генерация, а именно проверка;
- готовый документ уже есть, система его не создает с нуля;
- результат - список замечаний и рекомендаций по доработке;
- после проверки пользователь может вернуться в чат и внести правки.

## Развитие

### Что идет в развитие

- загрузка шаблона пользователем;
- сохранение проекта;
- шаблоны для разных подразделений;
- библиотека шаблонов;
- версионирование шаблонов;
- права доступа на шаблоны;
- переоткрытие сохраненного проекта;
- более богатая поддержка сценариев и источников.

### Почему загрузка шаблона важна

Это позволяет не ограничиваться шаблонами по умолчанию.

После доработки разные подразделения смогут:

- загрузить свой шаблон;
- использовать свои правила и структуру;
- работать в общем движке DocGen без переделки ядра;
- масштабировать продукт на несколько команд.

### Как заложить загрузку шаблона заранее

Даже если кнопки в MVP нет, в архитектуре нужно сразу предусмотреть отдельную сущность `Template`.

Что важно заложить:

- единый интерфейс для стандартных и пользовательских шаблонов;
- парсер шаблона как отдельный модуль;
- валидацию структуры шаблона;
- нормализацию шаблона в JSON;
- предпросмотр шаблона;
- версионирование;
- fallback на стандартный шаблон.

### Как заложить тему оформления заранее

Тему оформления в MVP не показываем, но архитектурно ее лучше не связывать жестко с форматом.

Что стоит предусмотреть:

- отдельный параметр `theme_id`;
- слой рендера между смыслом и форматом;
- возможность держать несколько визуальных пресетов для одного формата;
- независимость темы от шаблона;
- независимость темы от структуры документа.

Если это заложить сразу, потом можно без большой переделки добавить:

- разные визуальные темы для HTML;
- разные пресеты оформления для DOCX;
- корпоративные стили под подразделения.

Минимальный контракт шаблона:

- `id`
- `name`
- `type`
- `version`
- `owner_scope`
- `source_file`
- `parsed_schema`
- `required_sections`
- `prompt_rules`
- `output_mapping`
- `status`

### Как будет работать загрузка шаблона в будущем

1. Пользователь нажимает `Загрузить шаблон`.
2. Загружает `docx`, `md` или `json`.
3. Система проверяет структуру.
4. Сохраняет исходник и распознанную схему.
5. Добавляет шаблон в список выбора.

## Хранилище

### Базовая структура

```text
docgen/
  templates/
    default/
      use_case/
      html_article/
      docx_report/
    custom/
  sources/
  tmp/
  output/
  runs/
  config/
  projects/
```

### Что где лежит

#### `templates/default/`

Предзагруженные шаблоны, доступные в MVP.

#### `templates/custom/`

Папка для будущих пользовательских шаблонов.

#### `sources/`

Загруженные Word-файлы и ссылки текущей сессии.

Если проект не сохраняется, это временная зона.

#### `tmp/`

Промежуточные данные:

- распаковка Word;
- извлечение текста;
- промежуточный HTML;
- служебные артефакты генерации.

#### `output/`

Готовые результаты:

- `html`;
- `docx`;
- `pdf`.

#### `runs/`

Метаданные запусков:

- что запускали;
- с каким шаблоном;
- какими источниками;
- в каком формате;
- какой был статус.

#### `projects/`

Развитие.

Здесь будут сохраненные рабочие пространства:

- выбранный шаблон;
- привязанные источники;
- история изменений;
- состояние черновика.

## Что происходит после закрытия окна

### В MVP

- `tmp/` можно удалять;
- `sources/` живут только пока активна сессия или проект;
- `output/` остается, если результат уже сформирован;
- скачанный файл остается у пользователя.

### В развитии

- если проект сохранен, его можно открыть снова;
- если проект не сохранен, временные данные чистятся;
- шаблоны и результаты можно переиспользовать между сессиями.

## Интерфейс: как не усложнять

Для первого релиза лучше не дробить продукт на отдельные приложения и не строить два независимых workspace.

Оптимальная логика:

- один экран;
- один набор контролов;
- шаблон выбирается из стандартных;
- `Формат вывода` уже включает встроенное оформление результата;
- кнопка `Проверить по шаблону` рядом с `Собрать`;
- чат - для правок;
- предпросмотр - только для чтения;
- результат - через `Открыть` и `Скачать`.

## Вывод

MVP должен быть простым:

- шаблон выбирается только из предзагруженных;
- загрузка Word и ссылок уже работает;
- чат используется для правок;
- результат можно проверить по шаблону и скачать.

Развитие должно заложить:

- загрузку пользовательских шаблонов;
- сохранение проектов;
- масштабирование на разные подразделения;
- переиспользование движка без переделки ядра.

## Резюме по слоям

Для интерфейса достаточно двух сущностей:

- `Шаблон` - смысловая структура;
- `Формат вывода` - `HTML` / `DOCX` / `PDF` вместе с его встроенным стилем.

Тема оформления нужна только как скрытая архитектурная точка расширения, чтобы позже можно было отделить визуальный пресет от формата, если это действительно понадобится.
