# DocGen — требования к продукту

## 1. Назначение

DocGen — внутренний русскоязычный веб-инструмент для создания и проверки документов по предустановленным смысловым шаблонам.

Продукт помогает документалистам, аналитикам и сотрудникам учебных центров:

- создавать один новый документ из набора исходных материалов;
- проверять существующий документ по требованиям смыслового шаблона;
- исправлять результат вручную или через чат;
- выгружать готовый документ в нужном формате и корпоративном оформлении.

Обработка выполняется локальными моделями внутри корпоративного контура. DocGen использует только сведения из добавленных пользователем источников и не дополняет документы общими знаниями модели.

## 2. Цели продукта

- Сократить объём ручной работы при подготовке документов.
- Повысить качество и единообразие документов.
- Обеспечить проверку документов по структуре, полноте, терминологии, непротиворечивости и стилю.
- Поддержать корпоративные стандарты оформления для разных форматов.

Целевые показатели:

- на эталонном наборе документов корректно выполняется не менее 80% применимых проверяемых требований смыслового шаблона;
- не менее 60% документов из эталонного набора принимаются без существенной ручной переработки;
- задание из эталонного набора объёмом до 100 страниц обрабатывается не более пяти минут.

Существенной ручной переработкой считается изменение структуры документа или более 20% его содержательных элементов после результата DocGen. Конкретный способ подсчёта изменённых элементов фиксируется вместе с эталонным набором до приёмочного тестирования.

## 3. Пользователи

Основные пользователи:

- документалисты;
- аналитики;
- сотрудники учебных центров.

MVP рассчитан на однопользовательскую работу: один пользователь ведёт собственные документы и проекты. Авторизация и разделение доступа в MVP не требуются.

## 4. Основные понятия

### Смысловой шаблон

Определяет назначение, состав и структуру документа, обязательные сведения и правила проверки. Первые предустановленные шаблоны:

- FAQ;
- Use Case;
- техническое задание;
- Release Notes;
- API-документация.

Смысловые шаблоны хранятся и изменяются администратором в конфигурационных файлах. Пользователи не создают и не изменяют их через интерфейс.

### Шаблон оформления

Определяет визуальное представление документа в конкретном выходном формате: стили заголовков и текста, поля, колонтитулы, нумерацию, таблицы, цвета, логотипы и другие элементы брендирования.

Для одного формата может быть доступно несколько шаблонов оформления, например корпоративный, проектный или клиентский. Шаблоны оформления не определяют смысловой состав документа.

### Структурированный рабочий документ

Рабочая версия документа внутри DocGen, не привязанная к выходному формату. Она содержит:

- разделы, заголовки, абзацы, списки и таблицы;
- изображения и схемы;
- типы элементов документа;
- отметки о пробелах и замечаниях проверки.

Ручной редактор и чат изменяют эту рабочую версию. При экспорте DocGen применяет к ней выбранный шаблон оформления и создаёт итоговый файл.

## 5. Основные сценарии

### 5.1. Собрать документ

1. Пользователь создаёт или открывает сохранённый проект.
2. Добавляет исходные файлы и при необходимости ссылку на Confluence.
3. Выбирает смысловой шаблон.
4. Запускает сборку.
5. DocGen извлекает и интерпретирует содержимое источников.
6. DocGen создаёт один структурированный черновик строго по источникам.
7. Недостающие обязательные сведения отмечаются как пробелы и не заполняются предположениями.
8. Пользователь проверяет и редактирует результат.
9. Пользователь выбирает формат и доступный для него шаблон оформления.
10. DocGen формирует итоговый файл.

### 5.2. Проверить по шаблону

1. Пользователь создаёт или открывает проект.
2. Загружает существующий документ, например Use Case.
3. Выбирает смысловой шаблон.
4. Запускает действие «Проверить по шаблону».
5. DocGen проверяет документ и формирует отчёт о соответствии.
6. Пользователь исправляет документ вручную или через чат.
7. Пользователь повторяет проверку или выгружает обновлённый документ.

Режим «Проверить по шаблону» является самостоятельным сценарием и не требует предварительной генерации документа в DocGen.

## 6. Функциональные требования

### 6.1. Проекты

DocGen должен позволять:

- создавать проект;
- сохранять исходники, настройки и текущий рабочий документ;
- автоматически сохранять проект после добавления или удаления источника, изменения настроек, завершения сборки или проверки, ручного редактирования и применения правки через чат;
- открывать сохранённый проект и продолжать работу;
- хранить только актуальное состояние без истории версий и отката.

### 6.2. Источники

MVP должен поддерживать:

- DOCX;
- PDF;
- TXT;
- Markdown;
- PNG и другие распространённые растровые форматы изображений;
- изображения со схемами;
- страницы Confluence по ссылке.

DocGen должен:

- извлекать текст, структуру и таблицы;
- распознавать текст на изображениях;
- интерпретировать смысл, элементы и связи на схемах;
- объединять сведения из нескольких источников;
- использовать только добавленные источники;
- сохранять внутреннюю связь фрагментов рабочего документа с источниками для контроля обработки.

Показывать пользователю ссылки на источник для каждого фрагмента результата не требуется.

Максимальный общий объём одного задания — 150 страниц. Для документов с собственной пагинацией используется их фактическое число страниц; для TXT, Markdown и изображений объём рассчитывается после приведения содержимого к стандартной виртуальной странице. Параметры виртуальной страницы должны быть едиными для интерфейса и серверной проверки лимита. Для заданий объёмом от 101 до 150 страниц интерфейс должен предупреждать, что обработка может занять более пяти минут.

### 6.3. Сборка документа

DocGen должен:

- создавать один документ за один запуск;
- строить структуру по выбранному смысловому шаблону;
- переносить в документ только подтверждённые сведения из источников;
- отмечать отсутствие обязательной информации;
- не выдавать предположения модели за факты;
- показывать ход и итоговый статус сборки.

### 6.4. Проверка по смысловому шаблону

Проверка должна охватывать:

- наличие обязательных разделов;
- полноту обязательных сведений;
- соответствие структуры;
- корректность и единообразие терминологии;
- внутренние противоречия;
- соответствие заданному стилю текста.

Результат проверки должен:

- показывать найденную проблему и её расположение в документе;
- разделять подтверждённые проблемы и замечания с низкой уверенностью;
- отмечать аспекты, которые модель не смогла проверить надёжно;
- позволять перейти к исправлению документа;
- поддерживать повторную проверку после внесения изменений.

### 6.5. Редактирование

Встроенный редактор должен позволять вручную изменять:

- текст;
- заголовки и структуру разделов;
- списки;
- таблицы;
- расположение изображений и схем.

Изменения должны применяться к структурированному рабочему документу и сохраняться в проекте.

### 6.6. Чат

Чат должен позволять пользователю описывать требуемые изменения естественным языком.

DocGen должен:

- применять изменения к текущему рабочему документу;
- сохранять структуру документа, если пользователь не попросил её изменить;
- использовать только сведения из источников и текущего документа;
- отмечать невозможность правки, если для неё не хватает подтверждённых данных;
- показывать обновлённый результат после выполнения команды.

### 6.7. Экспорт

Поддерживаемые выходные форматы:

- DOCX;
- PDF;
- HTML;
- Markdown.

Порядок экспорта:

1. Пользователь выбирает выходной формат.
2. DocGen показывает шаблоны оформления, доступные для этого формата.
3. Пользователь выбирает шаблон оформления.
4. DocGen формирует файл из структурированного рабочего документа.

Для DOCX, PDF и HTML шаблон оформления должен поддерживать корпоративные стили, колонтитулы, нумерацию, таблицы и брендирование. Для Markdown применяются доступные шаблоны структуры и разметки без форматных возможностей, которых нет в Markdown.

## 7. Логика обработки

1. Источники проходят проверку формата и объёма.
2. DocGen извлекает из них текст, таблицы, изображения и структуру.
3. Изображения и схемы обрабатываются локальной мультимодальной моделью.
4. Извлечённое содержимое нормализуется во внутреннее структурированное представление с сохранением связи с источниками.
5. Смысловой шаблон задаёт структуру сборки или критерии проверки.
6. Результат сохраняется как структурированный рабочий документ.
7. Редактор и чат изменяют один и тот же рабочий документ.
8. При экспорте формат и шаблон оформления преобразуют рабочий документ в итоговый файл.

## 8. Ошибки и спорные ситуации

- Неподдерживаемый, повреждённый или защищённый паролем файл не принимается; пользователь получает понятную причину.
- Если текст, изображение или схема распознаны неуверенно, проблемный фрагмент помечается для проверки.
- Если Confluence недоступен или у пользователя нет прав, DocGen сообщает об этом и позволяет продолжить с остальными источниками.
- До запуска DocGen проверяет общий объём задания.
- Ошибка обработки одного источника не должна удалять остальные загруженные материалы.
- Если задание объёмом до 100 страниц не завершилось за пять минут, пользователь видит актуальный статус и может отменить операцию либо дождаться завершения. Повторный запуск доступен после отмены или ошибки.
- Частичный или неподтверждённый результат не должен обозначаться как готовый документ.
- Ошибка экспорта не должна удалять проект или рабочий документ.

## 9. Нефункциональные требования

### Безопасность

- Все документы обрабатываются внутри корпоративного контура.
- Для генерации и интерпретации используются локальные модели.
- Содержимое документов не передаётся внешним AI-сервисам.

### Производительность

- Поддерживаемый максимум — 150 страниц на одно задание.
- Целевое время обработки задания из эталонного набора объёмом до 100 страниц — не более пяти минут.
- Для более крупных заданий в пределах лимита допустимо большее время с обязательным отображением прогресса.

### Язык

- Интерфейс, смысловые шаблоны, обработка и результаты предназначены для русскоязычных документов.
- Поддержка английского языка и перевод не входят в требования.

### Надёжность

- Проект автоматически сохраняется после событий, перечисленных в разделе 6.1.
- Сбой сборки, проверки или экспорта не должен приводить к потере уже сохранённых данных.
- Длительные операции должны иметь понятные состояния: ожидание, выполнение, завершение и ошибка.

## 10. Проверка качества продукта

Для каждого смыслового шаблона создаётся эталонный набор русскоязычных источников, документов и ожидаемых результатов.

Проверяются:

- извлечение текста, таблиц, изображений и схем;
- соблюдение структуры смыслового шаблона;
- отсутствие сведений, которых нет в источниках;
- корректное обозначение пробелов;
- качество замечаний по полноте, терминологии, противоречиям и стилю;
- ручное и чат-редактирование без потери структуры;
- соответствие экспорта выбранному формату и шаблону оформления;
- сохранение и повторное открытие проекта;
- обработка ошибок и предельного объёма;
- достижение целевых показателей качества и времени обработки.

## 11. Этапы развития

### MVP

- однопользовательские сохранённые проекты;
- два равноправных режима: сборка и проверка;
- источники из файлов, изображений, схем и Confluence;
- локальные текстовые и мультимодальные модели;
- предустановленные смысловые шаблоны в конфигурационных файлах;
- ручной редактор и чат;
- экспорт в DOCX, PDF, HTML и Markdown;
- несколько шаблонов оформления для каждого формата;
- автоматическое сохранение;
- лимит 150 страниц.

### Будущее корпоративное развитие

- авторизация и поддержка нескольких пользователей;
- роли и разграничение доступа;
- публикация и обновление готовых документов в Confluence;
- дополнительные интеграции и типы ссылок после отдельного продуктового решения.

## 12. Не входит в текущие требования

- история версий и откат изменений;
- одновременное редактирование несколькими пользователями;
- комментарии и согласование;
- английский язык и перевод;
- самостоятельное создание смысловых шаблонов пользователями;
- использование внешних облачных AI-моделей;
- формирование комплекта документов за один запуск;
- обработка обычных и внутренних веб-страниц, кроме Confluence.
