## Чат: надёжные сценарии правок

**Проблема:** сейчас один общий вызов модели одновременно распознаёт намерение, читает все источники, формирует операции и проходит grounding. Пустой или нестрогий ответ модели выглядит для пользователя как общий отказ, хотя причина может быть в маршрутизации, недоступных источниках, нерелевантном контексте или схеме ответа.

**Цель:** для типовых действий чат должен предсказуемо либо применить правку с происхождением, либо показать конкретную причину и следующее действие. Модель не должна быть единственной точкой отказа для ручных и структурных команд.

### План

- [ ] Выделить маршруты намерений до вызова модели:
  - ручная вставка текста и позиционная вставка;
  - форматирование существующего блока;
  - структурирование без изменения фактов;
  - добавление FAQ/вопросов по источникам;
  - фактическое уточнение или переформулирование;
  - нераспознанный запрос с коротким уточняющим вопросом.

- [ ] Для FAQ сделать отдельный контракт результата: новая пара `Вопрос`/`Ответ`, один или несколько релевантных `evidence_block_ids`, место вставки и краткая сводка. Не позволять модели вставлять только вопрос без ответа или технические поля provenance в текст.

- [ ] Добавить локальный поиск источников перед моделью для всех фактологических сценариев: ранжирование блоков, ограниченный контекст, сохранение ID и цитат. Если совпадений нет, сообщать «не найден фрагмент источника по теме запроса», а не общий grounding-отказ.

- [ ] Кэшировать нормализованные блоки на время проекта/ревизии источников. Не извлекать заново все Confluence-страницы и файлы на каждое сообщение чата; сбрасывать кэш после изменения источников.

- [ ] Разделить ошибки в интерфейсе и API: нет источников, источник недоступен, нет тематического фрагмента, модель вернула некорректную схему, ответ не прошёл grounding, конфликт ревизий. Для каждой ошибки показать короткое действие: повторить, проверить источник или уточнить запрос.

- [ ] Ввести ограниченные повторные запросы модели по типу сценария: исправление JSON, повтор с релевантными блоками, повтор с требованием provenance. После лимита попыток не изменять документ и сохранять диагностический код причины.

- [ ] Добавить защищённую наблюдаемость: идентификатор запроса, тип сценария, число блоков до/после поиска, тип отказа, число повторов и длительность. Не писать полный текст источников и ответы модели в Docker-логи; включить отдельный диагностический режим с маскировкой данных для настройки модели.

- [ ] Собрать e2e-набор реальных сценариев: добавить вопрос по Confluence, вопрос без подтверждения, ручный текст, разделение на разделы, форматирование, битый JSON, нерелевантная citation, недоступный Confluence и конфликт ревизии. Проверять итоговый документ, provenance и текст ошибки.

### Критерии готовности

- Типовые запросы не заканчиваются общим «нет подтверждения», когда подходящий фрагмент источника существует.
- Каждая фактологическая правка имеет provenance, а ручной текст явно помечен как ручной.
- Чат не перечитывает все источники проекта для каждого сообщения без необходимости.
- При ошибке пользователь понимает, что именно произошло и что сделать дальше.
- Полные тексты документов и ответы модели не попадают в обычные production-логи.

**Оценка:** 1.5–3 рабочих дня, выполнять по этапам с включением сценариев через тесты.

## Полнота сборки по смысловым шаблонам

**Цель:** не допускать ситуацию, когда модель берёт из нескольких источников только часть материала, но сборка всё равно считается успешной.

**Подход:** не RAG и не отдельный реестр фактов. Все части выбранных источников детерминированно делятся на небольшие единицы, порциями преобразуются в элементы документа и затем проверяются по ID.

### План

- [ ] Добавить контроль `finish_reason`: не принимать ответ модели с `length` как готовый документ; уменьшать порцию и повторять вызов.

- [ ] Добавить разбиение `NormalizedBlock` на единицы покрытия со стабильными ID:

  - обычный абзац или PDF-блок — одна единица;
  - каждый пункт списка — отдельная единица;
  - каждая строка таблицы — отдельная единица с заголовками таблицы в контексте;
  - длинный абзац — на предложения или группы предложений;
  - заголовок не считать самостоятельным фактом, а передавать как контекст следующих единиц.

- [ ] Преобразовывать единицы небольшими порциями сразу в элементы выбранного шаблона. Каждый созданный узел должен ссылаться на использованные ID через уже существующий `provenance`.

- [ ] Не позволять модели молча отбрасывать содержательные единицы. Структурные элементы, пустые блоки и точные дубли исключать кодом до вызова модели.

- [ ] Собирать результаты порций в один верхнеуровневый узел на каждый раздел шаблона; полученные вопросы, шаги, требования и другие элементы хранить как дочерние узлы.

- [ ] После сборки детерминированно проверять:

  - каждая содержательная единица использована хотя бы один раз;
  - в документе нет неизвестных ID;
  - `locator` принадлежит исходной единице;
  - `quote` является точной непустой подстрокой исходного текста;
  - каждый верхнеуровневый `section_id` входит в выбранный шаблон.

- [ ] Повторно отправлять модели только непокрытые единицы. Ограничить число повторов; если пропуски остались, завершать задание ошибкой и не заменять предыдущий документ.

- [ ] Применить один общий механизм ко всем смысловым шаблонам: `faq`, `use-case`, `technical-spec`, `api-docs`, `release-notes`. Сценарий `no-template` не менять.

- [ ] Добавить тесты: два источника увеличивают покрытие; потерянная единица не даёт сохранить результат; повтор добавляет только пропущенное; `length` вызывает деление порции; все форматы экспорта и редактор сохраняют дочерние узлы.

### Критерии готовности

- Все содержательные единицы всех выбранных источников либо покрыты узлами документа, либо отброшены кодом как точные дубли/структурные элементы.
- Модель не может сама признать содержательную единицу неважной и молча исключить её.
- Неполный или обрезанный ответ не заменяет текущий документ.
- В итоговом документе нет служебных ID, цитат или технических комментариев.
- Текущие документы, редактор, чат, проверка и экспорт продолжают работать без миграции схемы документа.

**Оценка:** 4–7 часов. Изменение схемы базы и отдельный реестр фактов не требуются.
