# Разделение документа, смыслового шаблона и проверки

## Цель

DocGen хранит документ независимо от того, по какому смысловому шаблону его
проверяют. Один и тот же `SemanticTemplate` может выступать в двух ролях:

- `build_template_id` — схема намеренной сборки нового документа;
- `check_profile_id` — профиль одной проверки существующего документа.

Форматный Word-шаблон является третьим независимым входом. Для Use Case
содержательная структура берётся из восстановленного
`ШАБЛОНЫ/Шаблон+юзкейс.doc`, а корпоративные стили, обложка и колонтитулы — из
`app/tools/colvir_v3.dotx` через runtime-ассет `colvir.docx`.

## Модель документа

`WorkingDocument` получает явные метаданные:

- `origin`: `imported`, `assembled` или `manual`;
- `source_id`: источник импортированной рабочей копии, иначе `null`;
- `build_template_id`: смысловой шаблон сборки, только для `assembled`;
- `template_id`: временное совместимое поле старого API. Новая логика его не
  использует как профиль проверки.

Инварианты:

- `imported`: есть `source_id`, нет `build_template_id`;
- `assembled`: есть `build_template_id`, нет `source_id`;
- `manual`: оба поля пусты;
- профиль проверки никогда не записывается в документ.

## Проверка по смысловому шаблону

Вход: `target = current | source`, `check_profile_id`.

Для `source` workflow:

1. Нормализует источники и выбирает блоки только указанного `source_id`.
2. Создаёт импортированную рабочую копию без модельной пересборки. Заголовки,
   списки, таблицы и порядок блоков сохраняются.
3. Если в редакторе уже открыта копия того же источника, использует её текущую
   ревизию, чтобы проверять пользовательские доработки, а не импортировать
   источник повторно.
4. Передаёт модели только проверяемый документ и блоки выбранного источника.
5. Сохраняет рабочую копию лишь после полной валидации ответа модели.

Для `current` проверяется любая текущая рабочая копия: профиль не обязан
совпадать с `build_template_id`.

Результат проверки — внутренний sidecar, а не отдельный пользовательский
документ. Он привязан к проекту, ревизии документа, `check_profile_id` и
`target_source_id`. UI показывает замечания в результате проверки, а рабочая копия
остаётся открытой в редакторе для доработки.
После изменения документа старый запуск остаётся в истории, но считается
относящимся к предыдущей ревизии.

Ошибки различаются: target отсутствует, источник недоступен, в выбранном
источнике нет блоков, ответ модели невалиден, evidence отсутствует, ревизия
изменилась. При любой ошибке документ и история проверок не изменяются.

## Сборка по смысловому шаблону

`AssembleWorkflow` создаёт `origin=assembled` и записывает
`build_template_id`. После модели применяется template-specific adapter.

Use Case adapter:

- располагает секции в порядке смыслового шаблона;
- создаёт видимый heading для каждой включённой секции;
- обязательная секция без данных представляется подписанным структурным gap;
- `main-flow`, альтернативы и исключения допускают только отдельные элементы
  списка;
- предусловия допускают список или отдельные параграфы;
- голый параграф `Нет данных в источниках` запрещён;
- перед сохранением выполняется локальная структурная валидация.

FAQ остаётся отдельным adapter и не определяет общую модель документа.

## DOCX и PDF

Обычный импортированный документ экспортируется в своей текущей семантической
структуре. Собранный Use Case экспортируется через Use Case layout:

- корпоративные стили и Word numbering берутся из `colvir.docx`, собранного из
  `colvir_v3.dotx`;
- фиксированная структура и подписи полей соответствуют
  `Шаблон+юзкейс.doc`;
- создаются таблицы общих сведений, описания, технических спецификаций, ссылок
  и истории изменений;
- отсутствующие значения оставляют ячейки пустыми;
- обязательные строки и таблицы не удаляются;
- PDF строится из того же DOCX через LibreOffice, поэтому структура DOCX и PDF
  совпадает.

Экспорт повторно запускает локальную структурную валидацию собранного Use Case
и не создаёт файл при нарушении инвариантов.

## Совместимая миграция

1. Старый `WorkingDocument.template_id != no-template` читается как
   `origin=assembled`, `build_template_id=template_id`.
2. `template_id=no-template` читается как `origin=manual`.
3. Новые документы записывают явные поля; старое поле временно сохраняется для
   совместимости API, тестов и установок без одномоментной JSON-миграции.
4. Создаётся таблица истории проверок. Текущий согласованный legacy-отчёт из
   `ProjectArtifact` переносится туда один раз с профилем из
   `report.template_id` и текущей ревизией.
5. Legacy-поля `report_json/report_revision` временно отражают последний отчёт
   для совместимости UI. Источником истины становится история проверок.

## Проверки готовности

- корпоративный DOCX импортируется и проверяется без сборки;
- Confluence является check target и не запускает AssembleWorkflow;
- один импортированный документ имеет независимые проверки по двум профилям;
- Use Case assembly создаёт headings, подписанные gaps и отдельные list items;
- DOCX и PDF содержат корпоративные стили, полную форму Use Case и пустые
  ячейки для отсутствующих данных;
- невалидная модельная операция не изменяет документ или историю.
