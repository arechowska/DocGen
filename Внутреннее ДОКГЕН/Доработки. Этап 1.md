# DocGen — этап 1: подтверждённые защитные доработки

## Контекст

Задание сверено с кодом `cfc65ba` (`main`, `demo-ready-2026-08-25`).
Предыдущий security review был сделан для `820ab97`; после него код
существенно изменился. Severity и статусы находок нужно повторно
подтвердить на `cfc65ba` перед релизом.

Этап 1 не меняет YAML-шаблоны, кнопки и роутинг чата, но меняет
техническую логику: границы входа, доступ к файлам, логирование и
аудит. Каждая задача — отдельный PR с тестами.
Пути к продуктовому коду указаны относительно `app/src/docgen/`, а тесты —
относительно `app/`.

**Общие инварианты:**

- превышение лимита не меняет документ, ревизию, отчёт или job;
- данные не обрезаются молча: возвращается контролируемая ошибка;
- в PR фиксируются baseline commit, точные дефолты и форматы отказа;
- после каждого PR проходят целевые тесты и полный `pytest`.

## З1. Лимиты TXT/Markdown до материализации блоков

**Подтверждено кодом:** `TextExtractor` читает файл целиком;
`_extract_text()` вызывает `splitlines()` и создаёт `NormalizedBlock` для
каждой непустой строки. Markdown сначала целиком парсится в токены.
Лимит 150 виртуальных страниц применяется только после экстракции.

**Файлы:** `extraction/text.py`, `extraction/registry.py`, `config.py`,
`tests/extraction/test_text.py`, `tests/test_config.py`.

**Что сделать:**

1. До `MarkdownIt.parse()` и `text.splitlines()` проверить общее число
   символов, число строк и максимальную длину строки.
2. При создании блоков повторно контролировать число блоков и суммарный
   объём их текста.
3. Для Markdown ограничить строки и столбцы таблицы до создания `rows`.
4. Превышение — `ExtractionError`; никакого частичного результата.
5. Вынести лимиты в `Settings` и прокинуть через `ExtractorRegistry.default()`.

**Действие агента в этом PR:** измерить обычные и патологические fixtures,
выбрать и зафиксировать один точный набор дефолтов, а также указать, считаются ли
пробелы в квоте 150 страниц. Внешнее решение для старта не требуется; не оставлять
в коде диапазоны вида «2–4 МБ».

**Приёмка:** патологическая длинная строка, миллионы коротких строк и
большая Markdown-таблица отклоняются рано; граничные и обычные файлы
дают прежние блоки и `page_units`.

## З2. Лимиты тела запроса и рабочего документа

**Подтверждено кодом:** `/editor/save` ограничен
`MAX_WORKSPACE_HTML_CHARS = 20_000_000`, а не 500 000. Для текста узла,
строк списка, ячеек таблицы и `alt` нет лимита длины. `apply_operations()`
делает `model_copy(deep=True)` до проверки размера результата.

**Файлы:** `main.py`, `editor/routes.py`, `editor/validation.py`,
`documents/operations.py`, `documents/edit_service.py`, `documents/repository.py`.

**Что сделать:**

1. Ввести потоковый server-level лимит тела. Не доверять только `Content-Length`:
   лимит работает и для chunked/отсутствующего заголовка.
2. Добавить `max_length` для `text`, элемента списка, ячейки таблицы и `alt`.
   Сохранить лимиты 100 элементов списка, 100 строк и 20 ячеек в строке.
3. Ограничить сериализованный `WorkingDocument` в UTF-8 байтах. Проверять до
   deep-copy, где это возможно, и обязательно до записи в БД.
4. Одинаково ограничить JSON и form-эндпоинты.
5. Возвращать `413` для превышения тела и `422` для поля/итогового документа.

**Действие агента в этом PR:** измерить в байтах реальный большой документ и
зафиксировать один дефолт с запасом. Внешнее решение для старта не требуется;
не вводить 5–10 МБ без сверки с действующими 20 млн символов.

**Приёмка:** превышение каждой границы не меняет состояние; запрос без
`Content-Length` тоже ограничен; типовой большой документ сохраняется и
экспортируется; конкурентный edit по-прежнему даёт `409`.

## З3. Project-scoped доступ к изображениям при экспорте

**Область PR — только security-fix.** Поддержка новых картинок из
DOCX/PDF/Confluence вынесена в Этап 2.

**Подтверждено кодом:** `local_storage_image_loader(storage)` разрешает
любой безопасный относительный путь внутри общего `data_dir`. Loader не знает
`project_id` и не проверяет принадлежность источника.

**Файлы:** `export/html.py`, `export/docx.py`, `export/pdf.py`,
`jobs/worker.py`, `generation/routes.py`, `sources/storage.py`, `sources/repository.py`.

**Что сделать:**

1. Loader получает `project_id` и читает только из `projects/<project_id>/sources/`.
2. Если ссылка содержит `source_id`, проверять `source.project_id == project_id`.
3. Отклонять абсолютный путь. Для новых media в Этапе 2 использовать
   непрозрачный `media_ref`, а не произвольный `storage_path`.
4. Одинаково обновить background export и synchronous conversion.
5. Не добавлять fallback на произвольный `content_base64`.

**Приёмка:** файл текущего проекта читается; путь в другой проект, `..`,
backslash, absolute path, symlink-escape и неизвестный `source_id` отклоняются;
все три формата и оба export-пути имеют одинаковую политику.

## З4. Структурная наблюдаемость и журнал действий

**Важно:** печать полного AI-запроса, сырого ответа и `content` уже удалена
из `ai/client.py`. Задача — защита от регрессии, метрики и аудит.

### PR 4A. Логи и AI-diagnostics

- лог на AI-вызов и job: correlation/request ID, `job_id`, сценарий,
  provider/model, размеры, число блоков, `finish_reason`, класс ошибки,
  попытки и длительность;
- в обычном логе нет prompt, source/document text, response content, credentials
  и `Authorization`;
- один режим `DOCGEN_AI_DEBUG_MODE=off|masked|full`, дефолт `off`;
- `full` запрещён в production-профиле; каталог `0700`, файлы `0600`,
  валидированные ID в именах и атомарная запись;
- точные `max_files` и `max_age_hours`; очистка при запуске и перед записью;
- в `masked` не хранить длинные фрагменты; хеши солить эфемерным секретом.

### PR 4B. Журнал действий

- SQLAlchemy-модель и миграция через текущий `initialize_database()`;
- event ID, UTC time, correlation ID, subject, action, outcome, `project_id`, `source_id`,
  `job_id`, document revision — без контента;
- успешные/отклонённые мутации, запуск/отмена job, экспорт и Confluence calls;
- success-событие не остаётся после rollback бизнес-операции;
- audit repository не имеет UPDATE/DELETE; есть тесты append-only контракта;
- до auth `anon`/сессия — операционная корреляция, а не доказательная
  атрибуция пользователя.

**Приёмка:** во всех режимах в обычном логе/audit нет marker-строк из
источника, документа и response; full/masked capture соответствует режиму;
на одну успешную мутацию — ровно одно success-событие.

## Порядок и границы

1. З1 и З2 можно делать независимо.
2. З3 можно делать параллельно, но он затрагивает оба export-пути.
3. PR 4A предшествует PR 4B: он задаёт correlation ID.
4. После Этапа 1 агент выполняет Этап 2. Архитектурная и security-виза —
   критерий приёмки готового кода, а не входной блокер.

## Вне области Этапа 1

- аутентификация, владелец/тенант проекта и ACL;
- доверие к proxy identity и выбор OIDC/basic/reverse-proxy auth;
- делегированный доступ к Confluence;
- user/tenant quotas и rate limiting;
- YAML-шаблоны и агентная переделка чата.
