# DocGen — этап 2: доработки для AI-architecture и security-визы

## Цель и порядок

Этап 2 выполняет агент после Этапа 1. Цель — получить визу архитектора ИИ
и безопасника на готовый код, тесты и задокументированные остаточные риски.

Решения ниже уже фиксированы. Предварительная виза для старта не требуется.
Если агенту нужно отступить от контракта, он останавливает только зависимый PR
и описывает причину. Каждая задача — отдельный PR; каждый PR указывает baseline
commit, тесты и migration/rollback при изменении данных.

Пути к продуктовому коду указаны относительно `app/src/docgen/`.

## З5. Media pipeline: DOCX, PDF и Confluence до экспорта

**Подтверждено кодом:** DOCX не создаёт `BlockKind.IMAGE`; PDF читает только
`page.get_text("blocks")`; Confluence держит attachment в `content_base64`;
`enrich_images()` удаляет media reference; `ImageExtractor` передаёт абсолютный путь.

**Фиксированный контракт:**

1. Добавить `media_assets`: UUID `id`, `project_id`, `source_id`, internal
   `relative_path`, `media_type`, `size_bytes`, SHA-256, width, height, `created_at`.
2. Запись и чтение идут только через media service с контекстом `project_id`.
3. `DocumentNode.data.media_ref` хранит только UUID `media_assets.id`.
4. Resolver проверяет `media_asset.project_id == current_project_id` и принадлежность
   `source_id`; путь из узла никогда не резолвится напрямую.
5. Удаление source/project удаляет media; rollback не оставляет сирот.
6. MIME проверяется по содержимому. Лимиты: bytes, pixels, count на source,
   total media bytes на source/project.
7. Preview читает media через project-scoped route и тот же resolver, что экспорт.
   Data-URL в `rich_html` не использовать.

**Поставка:** media storage/lifecycle → Confluence → DOCX/fidelity → PDF → end-to-end export.

**Приёмка:** для каждого типа работает `extract → persist → assemble/convert →
HTML/DOCX/PDF`; проверены cleanup, limits, PDF scan/mask/alpha/CMYK, дедупликация
`xref`, Confluence redirects/SSRF и межпроектный отказ.

## З6. Строгий grounding для смысловых шаблонов

**Уже реализовано — не переделывать:** `finish_reason=length` отклоняется;
`_assemble_batch()` делит batch; `_run_batched_assembly()` объединяет пакеты;
`_validate_coverage()` ищет непокрытые блоки; section ID проверяются.

**Дефект:** `GroundingValidator.validate()` игнорирует `source_blocks` и проверяет
только gap. `quote`, `locator` и block ID не валидируются; coverage пока warning.

**Фиксированная модель provenance:**

- `source_id` — реальный `Source.id`;
- новое обязательное `block_id` — `NormalizedBlock.id`;
- legacy JSON, где старое `source_id` содержит block ID, мигрируется при чтении:
  значение переносится в `block_id`, Source ID восстанавливается из префикса
  нормализованного block ID;
- новые prompt/code не подменяют одно поле другим.

**Фиксированный режим:** `lossless` для `faq`, `use-case`, `technical-spec`,
`api-docs`, `release-notes`. Каждая содержательная единица должна быть покрыта.
`no-template`, импорт и ручной текст эта проверка не затрагивает.

**Что сделать:**

1. Проверять source/block pair, точную непустую `quote` и `locator`.
2. Валидировать provenance всех фактических дочерних узлов.
3. Разбить блоки на единицы: абзац/PDF-block, list item, table row;
   длинный абзац — на стабильные группы предложений.
4. Точные дубли и структурные единицы исключать кодом до модели.
5. Повторять только непокрытые единицы с лимитом попыток.
6. После лимита падать, не заменяя прежний документ и revision.

**Приёмка:** unknown ID, wrong locator, empty/inexact quote и uncovered unit не
дают сохранить результат; дочерние узлы проверяются; legacy documents читаются;
существующие batching/length тесты остаются зелёными.

## З7. Снижение риска prompt injection

**Граница:** prompt снижает риск, но не гарантирует защиту. Контроль дают
ограниченные capabilities и детерминированная валидация.

**Что сделать:**

1. В assemble, check и factual chat маркировать source/document blocks как untrusted data.
2. В system prompt запретить трактовать вложенные instructions, role/system tags,
   URL и поддельные schemas как команды.
3. Не добавлять model tools, network calls или secret access.
4. Сохранить Pydantic/schema, section/rule IDs, grounding, operation allowlist, revision checks.
5. Добавить adversarial fixtures: TXT, DOCX, Confluence HTML, hidden text, fake system tags,
   section/rule ID и JSON-schema substitution.

**Приёмка:** на каждом fixture выход либо проходит все проверки, либо отклоняется
без изменения состояния. Не требовать недоказуемое «инъекция никогда не сработала».

## З8. Совместимость structured output

**Подтверждено кодом:** `model.startswith("qwen")` отключает `response_format`;
остальные модели считаются совместимыми с strict `json_schema`.

**Фиксированный контракт:** `DOCGEN_STRUCTURED_OUTPUT_MODE=json_schema|plain_json`.
Дефолт `json_schema` сохраняет текущее поведение для не-Qwen; для текущего Qwen
в deployment config явно задать `plain_json`. В обоих режимах обязательна
локальная Pydantic validation. Проверку имени модели удалить.

**Приёмка:** payload и response validation протестированы для обоих режимов;
несовместимая модель не получает `response_format`; malformed JSON безопасно отклоняется.

## З9. Временное усиление контура доступа

**Фиксированная deployment model:** trusted single-user service во внутреннем контуре.
Публичный и multi-user deployment запрещены до отдельного auth/ACL эпика.

**Агент делает отдельными PR:**

1. В локальном compose — `127.0.0.1:8000:8000`; Dokploy сохраняет `expose`.
2. Если принимается proxy identity: явный header, trusted proxy IP/CIDR,
   fail closed для direct request, missing/duplicate header.
3. Текущая Confluence service account — least privilege; allowlist по canonical
   space/page ID; redirects проходят повторную проверку.
4. Атомарные глобальные потолки: projects, storage bytes, queued/running jobs.
5. README и deployment config предупреждают: не публиковать сервис без
   trusted reverse proxy, который сам выполняет authentication.

**Вне этого этапа:** встроенные auth, ownership, ACL, delegated Confluence access,
tenant/user quotas и rate limiting — отдельный multi-user эпик. Глобальные quota checks всё
равно должны быть защищены от race condition.

## Приёмка и получение визы

- повторный security review итогового commit, а не перенос статусов с `820ab97`;
- AI-architecture review **готового кода и тестов** З6–З8;
- security review **готового кода и deployment assumptions** З5, З7 и З9;
- regression: editor, generation, chat, export, migrations и journey tests;
- в logs/audit/fixtures нет secrets и полного контента;
- описаны env defaults, deployment assumptions, migration/rollback и остаточные риски;
- виза считается полученной только после закрытия reportable findings или
  явного принятия каждого остаточного риска.
